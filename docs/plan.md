# 計画：ことづて（AIで動くOSMビューア）

表記：**[事実]** 一次資料かコードで確認、**[報道]** 報道で確認、**[推測]** 推論・調べた範囲での判断、**[未確認]** 確かめられていない。

## 1. 一言で

地図に詳しくない社員が、日本語ひとことで、出典つきの「渡せる地図」をつくる。Googleにも、公開サーバにも頼らずに。

- 社外にも渡せる成果物：出典とデータ時点を焼き込んだ画像、共有リンク。
- 社内用の成果物：GPX、Claudeなしで再実行できるレシピ（行った操作の並びを記録したJSON）。
- 根拠になった OSM の要素IDとデータ時点を示し、タグがなければ「判定不能」と正直に出す。

## 2. 背景

- 想定する場面（架空）：地図に詳しくない社員が、コースづくり、場所の確認、資料への地図の埋め込みに、一般向けの地図サービスを使っている。
- 無償で契約もSLAもないサービスに業務を頼ると、提供条件や規約が変わったときに業務が止まるおそれがある [推測]。
- 以前の推薦は「試走コース・コンパイラ」だったが、ユーザーがビューアへの切り替えを決めた。その後の調査と評価では「ビューアを土台に深い機能を1つだけ主役にする」案も示されたが、4つの操作を均等に作る方針になった。

## 3. 4つの操作の作り込み

| 操作 | 作り込み |
|---|---|
| (a) 場所・住所 | 住所はデジタル庁の abr-geocoder で解決し、座標の精度（住居番号の位置／丁目の代表点／町の代表点。応答の `coordinates_level` から作る）を言い換えずに表示する。施設名は OSM で表記ゆれ（name、name:ja、alt_name など）も含めて探し、候補を選ばせる。見つからなければ見つからないと言う |
| (b) 地物の絞り込み | 業務の言葉と OSM タグの辞書を作る。含めるタグと除くタグも辞書に持たせる（例：トンネル＝道路の `tunnel=yes`、建物の通り抜けと暗渠は除く）。画面には「解釈：踏切＝`railway=level_crossing`（歩行者専用は含まない）」のように、どう解釈したかを常に出す。0件は「OSM上で0件（現地にないとは限らない）」 |
| (c) ルート・試走コース | 自前の Valhalla で引く。「高速を使わない」はハード除外。合否はルート上の way の生のタグを Overpass で取り直して機械的に判定し、タグがなければ判定不能。トンネルの数え方（連続する `tunnel=yes` を1本、50m未満は除外）を表に明記する。経由地の候補は AI ではなくプログラムが作る（最大5案、ルート計算は最大10回） |
| (d) 資料用の地図・共有 | 出典とデータ時点を焼き込んだ画像。共有リンクは地図の状態をサーバに保存して短いIDで参照する。GeoJSON と GPX にはライセンス情報を埋め込み、社外に渡すときは注意を出す（ODbL の継承条件があるため [事実]） |
| OSMノートの下書き | 確認方法を選ばせ（「Googleマップで見た」は選べない）、社名や「試走」などの語が入っていたら止める。アプリは OSM と通信せず、下書きのコピーまで。投稿は現地を見た本人 |

## 4. 構成

```
日本語の依頼 → Claude（型付きの操作を選ぶ） → 自社のサービスで実行（住所・地物・ルート） → 結果からテンプレートで文章 → 渡せる成果物
```

- 地図：Protomaps の PMTiles（東京の範囲）＋ basemaps-assets を自前配信。MapLibre GL JS。
- 地物検索：Overpass（関東データ）。ルート：Valhalla（同じ関東データ）。住所：abr-geocoder。
- Overpass と Valhalla の Docker イメージには Apple Silicon（arm64）版がある [事実]。
- Claude API はサーバ側から呼ぶ。MCP サーバは AI を呼ばず、キーも持たない。
- 型付きの操作（約12個）：search_place、geocode_address、find_features、route、check_route、set_view、add_pin、highlight、make_share_link、export_png、export_gpx / export_geojson、draft_osm_note。

### 存在しない場所や数を出さない仕組み

- 位置の指定は参照だけ。LLM が覚えている座標は受け付けない。
- Overpass QL は LLM に書かせない。辞書から選んだタグでプログラムが組み立てる。
- 画面の文章はツールの結果からテンプレートで作る。結果にない名前や数字は表示しない。
- 0件、判定不能、辞書にない言葉は、そのとおりに表示する。
- OSM の description、note、fixme など誰でも書ける自由文のタグは LLM に渡さない。

## 5. Claude の使い方

- 実行時：型付きツール。業務の言葉の辞書を1つのファイルにまとめ、検索の組み立て、ツールの選択肢、Skill で共通に使う。MCP の見せ場は一括作業（23区の区役所の住所一覧から、ピンと資料用の画像をまとめて作る）。レシピを保存して Claude なしで再実行できるようにする。
- 開発時：hooks（公開サーバのURLを止める、出典表示の検査、型チェックと簡易評価が通るまで終わらせない）、サブエージェント（eval-runner、tag-auditor）、評価セットの先コミット。

## 6. 評価

- 日本語の評価セット40問（各操作10問）。結果が正しいかで採点（住所は正解から100m以内、地物はタグの一致、など）。プロンプト調整の前にコミットする。
- 罠の問い10問（東京の外、存在しない施設、辞書にない言葉）。「見つからない／対応外／判定不能」と正しく答えたか。
- 捏造の回数（結果にない名前や数字を表示した回数）。目標0回。
- 改善の記録（3回分）。
- 使いやすさテスト（家族や友人2〜3人、1人20分）。

## 9. リスク

| リスク | 対策 |
|---|---|
| 汎用的な「AI地図チャット」と見られる（4つの操作を同じ重さで並べた案に対する AI 評価役の推定はインパクト2、デモ3、Claudeの活用2、深さ2。公式審査ではない） | デモを1本の仕事でつなげ、各操作に汎用ツールにない場面を置く。先行例との違いを自分から言う |
| 既存OSSの使用が規則に反する可能性 | 運営に問い合わせる。README と動画で、期間中に作った部分と使ったOSSを分ける |
| 日本の OSM に車線や規制のタグが少ない | 確実に測れる条件（トンネル、高速、時間）を中心にし、判定不能はそのまま見せる |
| 日本語の施設名の検索が弱い | 表記ゆれを吸収し、候補を選ばせる。住所は ABR で解決 |
| 構築に想定以上の時間がかかる | M0、M1 の節目で判断し、削る順に従う |
| Claude API も依存先になる | 契約のある有償APIとして扱い、レシピの再実行で Claude が止まっても地図を出せるようにする |
