## 1. 目的と、なぜ

- 地図アプリを作る人が、1つのコマンドに地域を渡すだけで、全部のセットアップが終わるようにする。例：`npm run setup -- --region=kanto`、`--region=japan`。
- 普通のノートPC（メモリ 8〜16GB の Mac か Linux）に入るよう、ディスク・メモリ・時間・ダウンロード・入れるソフトの数を、できるだけ減らす。大きなサーバを要らなくする。
- 約束の①「あなたの地図を、あなたのマシンに」を本当にするため（2026-11-06 にユーザーが決定）。
- 同時に、地図の地点をクリックすると詳細が出るようにする（2026-11-06 にユーザーが決定）。

## 8. 部品ごとの作り

### 8.1 検索データ（Overpass の代わり）

- アプリの中で `node:sqlite` で読む SQLite のファイル1つ。関東で 0.29〜0.33GB（Overpass は 7.4GB）、作るのに約31秒（Overpass の初期化は10分以上）、1回の検索は 0.1〜5ms（Overpass は 179〜1236ms）[事実]。日本全国は約1.4〜1.6GB、作るのに約2.5分 [推測]。
- 中身：辞書の言葉に当たる地物（範囲の索引つき）、名前の検索（完全一致の表と、3文字以上の部分一致の trigram の索引）、ルートの判定用に道（highway の way 全部）のタグ、地点の詳細用のタグ（§9）、データ時点。
- 辞書（`src/ops/dict.ts`）はそのまま唯一の元。作るスクリプトが dict の条件の書き方（`=`、`~`、`!~`、`,i`）を読む。辞書を変えたら検索データを作り直す（関東で約31秒）。
- Overpass と同じ答えにするため、わざと同じにすること：距離の地球の半径（1e7/90 m/度）、結果の順（種類、ID）と 201件の上限、ルートの回廊の検索は間引いた点を結んだ線の周り、試走コースの道路の条件は上限より先に当てる、否定の条件はキーのない要素を通す。4つの実際の問い合わせ（点の周り、名前、6km のトンネル、300m の回廊）で、要素・順・座標・形が全部一致した [事実]。
- 違いうるところ：名前だけで探す way と relation は、範囲の判定が bbox の重なりになる（Overpass より少し広い）[推測]。全角英字の大小の扱い [未確認]。どちらも §10 の比べる確認で見る。
- コード：`src/services/osm.ts` に4つの関数（辞書の言葉、名前、way のタグ、試走コースの候補）＋地点の詳細。中は Overpass と SQLite の2つを持ち、環境変数 `OSM_BACKEND` で選ぶ。**コードの既定は overpass**（Q1・Q2 の確認が済むまで）。提出のあとで Overpass の分を消す。
- 呼ぶ側（find_features、route、search_place、plan_course、check_route）は、関数の呼び方が変わるだけ。toPlace、トンネルと踏切のまとめ、範囲の判定、並べ替えは変えない。
- ファイルは最初の検索のときに開く。なければ「検索データがありません。`npm run setup` を回してください」と出す（MCP を別のフォルダから起動しても、check-quick でも壊れないように）。
- 画面の言葉（Q3）：「札は AI を通さずに、自社の Overpass へ直接たずねます」→「札は AI を通さずに、手元の検索データ（OSM）から直接さがします」。エラーの「地物の検索（自社の Overpass）に接続できません」→「検索データ（OSM）を読めません」。外部通信の記録の「自社のサービス」の数は、検索の分だけ減る（通信していないので数えない）。README の使ったOSSの表から Overpass が外れ、SQLite（Node に入っている）が入る。

### 8.2 ルート（Valhalla）

- 同じイメージ（版を digest で固定）。セットアップで tar を1つ作り、それだけで動かす。関東：2.41GB → 0.90GB、メモリ 2.1GB → 55〜125MB。26本のルートで、時間・距離・曲がり方・通る道の並びが今と全部同じ [事実]。
- 変えること：admins.sqlite と timezones.sqlite を作らない（結果は同じ。左側通行の判定 `drive_on_right=false` も今と同じ [事実]）。タイルのフォルダと pbf の写しを消す。待ち受けのスレッドを30から2に（メモリはスレッドの数で決まる）。作るときの `-j` は既定2（関東の最大メモリは -j2 で 4.6GB、-j8 で 5.3GB）。
- 変えないこと：速度は今と同じ全体の既定値を使う（関東のデータには日本の境界がないので、日本の速度の行は今も使われていない。デモの 13.1分・21.2分はこれに依る [事実]）。
- 東京で Valhalla のデータを東京の bbox＋0.1度に切ると、さらに 455MB 減る。ただし CLAUDE.md の決定「検索とルートのデータは関東全体で作る」を変えることになり、デモの経路で確かめていない。凍結の前はやらない（§13）。

### 8.3 住所（ABR）

- 今は PostgreSQL と ABR の2つのコンテナ（約315MB）。調べると、住所の答えを返す `abrg serve` は DuckDB のファイル1つ（東京で 22MB）しか読まない。PostgreSQL は作るときだけ要る。PostgreSQL なしで、18の住所で今と全部同じ答え（座標、一致した文字、残り、精度）、メモリ 40〜90MB [事実]。
- 作るときは、今の `scripts/abr-import.sh` と同じ順（init → import → cache build）。そのあと DuckDB のファイルだけ残し、PostgreSQL と作業の残りを消す。
- Docker の作業の残り（Go のイメージとモジュールで 6〜7GB [事実 この Mac]）を残さないため、compose の build を使わず、Go のコンテナでプログラムを作って、セットアップが作ったものだけを消す。PostgreSQL は外にポートを出さない（今のデモの 55432 とぶつからない）。上流の Dockerfile と同じ作り方の指定を写す。
- `abrdb` は1つの都道府県か全国しか取り込めない [事実]。複数の県の地域は Q5。
- 「港区芝公園4-2-8」は今も街区の代表点（`rsdtdsp_blk`）。住居番号の点はない [事実。HANDOFF にも記録あり]。

### 8.4 地図タイルとフォント

- 拡大の上限は15のまま。14にすると約3分の1になるが、拡大したときの建物が約1%、地点が約15%しか残らない [事実]。日本全国だけ `--maxzoom=14` を選べるようにする。
